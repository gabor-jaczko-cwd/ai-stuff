# Respond to Code Review

## Quick Start

Run this skill after receiving a code review — either GitHub PR comments or a local branch review generated by the `review` skill. It will triage all open findings, build a plan, implement fixes, and record the outcome.

## Mode Detection

On startup, detect which mode to use:

1. Identify the current branch: `git branch --show-current`
2. Check `./tmp/review-branch-<name>.md` (replacing `/` with `--`) for a local review save file
3. Check GitHub for an open PR on this branch

| Save file found | PR found | Mode |
|----------------|----------|------|
| No | Yes | **PR mode** |
| Yes | No | **Local mode** |
| No | No | Ask the user to clarify |
| Yes | Yes | Ask the user which source to use |

---

## Workflow

### 1. Load Review Source

**PR mode:**
- Find the open PR for this branch on GitHub and note its author (`<pr-author>`)
- Collect findings from **every** review on the PR, not only the latest one. Fetch reviews, inline threads and PR-level comments in one GraphQL call (paginate any connection whose `pageInfo.hasNextPage` is true):

  ```bash
  gh api graphql -F owner=<owner> -F repo=<repo> -F pr=<number> -f query='
    query($owner:String!,$repo:String!,$pr:Int!){
      repository(owner:$owner,name:$repo){
        pullRequest(number:$pr){
          author{login}
          reviews(first:100){ pageInfo{hasNextPage endCursor}
            nodes{ databaseId author{login} state body submittedAt commit{oid} url } }
          reviewThreads(first:100){ pageInfo{hasNextPage endCursor}
            nodes{ id isResolved isOutdated path line
              comments(first:50){ nodes{ databaseId author{login} body createdAt url
                originalCommit{oid} pullRequestReview{databaseId} } } } }
          comments(first:100){ pageInfo{hasNextPage endCursor}
            nodes{ databaseId author{login} body createdAt url } }
        }}}'
  ```

- Build the candidate list from two sources:
  1. **Unresolved inline threads** — every thread with `isResolved: false`, whichever review it came from. Keep the thread context: collapse to the last 3 messages if long, but always include the original comment and the most recent reply. Keep outdated threads (`isOutdated: true`) and mark them — they feed the "likely already addressed" check in Step 2.
  2. **Unanswered review bodies** — every review with a non-empty `body`, by someone other than `<pr-author>`, that is *unanswered* (see below). Skip bodies with nothing actionable ("LGTM", "see inline comments", a bare approval) — they need no reply.

  A review body is **unanswered** unless, after it was submitted, `<pr-author>` either posted a PR-level comment that @-mentions the reviewer, or replied in one of that review's inline threads. (PR-level comments are fetched only for this check.)
- Ordinary PR conversation comments (not part of a review) are **not** a source — this skill never responds to them.
- **Deduplicate** the candidates before triage. When two candidates raise the same concern — a review body restating one of its inline comments, the same point repeated in a later review round, two reviewers flagging the same problem — merge them into one item that lists every source (comment/review ID and reviewer). Merge on the *concern*, not merely the same file or line; when unsure, keep them separate and note the possible overlap in the plan.
- If nothing is left, report _"No unresolved threads or unanswered reviews on this PR."_ and exit.

**Local mode:**
- Read `./tmp/review-branch-<name>.md`
- Check `status` in the frontmatter:
  - `completed` → proceed
  - `in_progress` → warn: _"Review is still in progress; findings may be incomplete. Finish the review first, or continue anyway?"_ — wait for the user before proceeding
- Extract all findings from the findings table; skip rows whose severity cell begins with `[RESOLVED]` or `[REJECTED]`
- If no open findings remain, report _"All findings are already resolved or rejected."_ and exit

### 2. Triage

For each open item:

- **Categorise**: bug fix / style / design / question / nit
- **Prioritise**: blocker > major > minor > nit
- **Validate**: determine if the concern is legitimate given the codebase context
- **Pre-triage git check (PR mode):** check whether the file/line referenced by the comment has been modified in commits made *after* the review was posted (`git log --oneline <review-commit>..HEAD -- <file>`, where `<review-commit>` is the commit *that item's* review was made against — reviews from different rounds have different commits; for a merged item use the oldest source). If so, flag the comment as "⚠️ likely already addressed (commit <sha>)" in the plan — do **not** auto-resolve; confirm with the user during Step 3 before treating it as open work.

If an item is ambiguous, note the question inline in the plan (Step 3) — one targeted question per item. Do not use the `grill-me` skill.

### 3. Build a Plan

Produce a prioritised action list. For any ambiguous items, include the clarifying question inline under that item and wait for the user to answer before finalising the plan. For any items flagged as "likely already addressed," ask the user to confirm whether they are resolved.

**PR mode** — reference GitHub comment/review IDs, reviewers, and thread context. Label each source by kind (`Comment #<id>` for an inline thread, `Review #<id>` for a review body); a merged item lists all its sources:
```
## Review Response Plan

Reply style: <individual replies | single grouped reply>
Tests: <test command | none found>
Re-request review from: @<login1>, @<login2>

### Blockers
- [ ] Comment #<id> (@<reviewer>): <summary> → <proposed fix>
  > Thread: <last message in thread, if any>
  Reply: <full reply text — individual style>
- [ ] Comment #<id> (@<reviewer>) + Review #<id> (@<reviewer>, body): <summary> → <proposed fix>
  > Merged: same concern raised inline and in the review summary
  Reply: <full reply text>

### Major
- [ ] Comment #<id> (@<reviewer>): <summary> → <proposed fix>
  Reply: <full reply text>

### Minor / Nits
- [ ] Comment #<id> (@<reviewer>): <summary> → <proposed fix>
  Reply: <full reply text>

### Likely Already Addressed (confirm)
- ⚠️ Comment #<id> (@<reviewer>): <summary> — modified in <sha>. Already resolved? [yes/no]

### Rejected (with reason)
- Comment #<id>: <reason for not acting>
  Reply: <full reply text explaining why>

### Clarifications Needed
- Comment #<id>: <one targeted question>

### Grouped reply   ← grouped style only; replaces the per-item Reply lines
<full text of the grouped PR-level comment, exactly as it will be posted>
```

Every `Reply:` (or the grouped reply) is the complete text that will be posted — never a summary or "see file".

**Local mode** — reference finding row numbers and file/line:
```
## Review Response Plan

### Blockers
- [ ] Finding #<n> — <file>:<line> (🔴 Critical): <summary> → <proposed fix>

### Major
- [ ] Finding #<n> — <file>:<line> (🟡 Warning): <summary> → <proposed fix>

### Minor / Nits
- [ ] Finding #<n> — <file>:<line> (🔵 Nit): <summary> → <proposed fix>

### Rejected (with reason)
- Finding #<n>: <reason for not acting>

### Clarifications Needed
- Finding #<n>: <one targeted question>
```

**PR mode:** draft a reply for each item — whether actioning it or declining it — and write them to the reply file (see "Reply file" below) before presenting the plan. **Show the full text of every reply in the plan itself**, directly under its item (and the whole grouped reply, in grouped style), plus the list of reviewers to re-request — the user must be able to review everything in the conversation without opening any file. State the **reply style** at the top of the plan (see "Reply style" below): _individual replies_ or _single grouped reply_.

**Both modes:** find the test command in the project guidelines (CLAUDE.md, Makefile, package.json, composer.json, etc.) and state at the top of the plan which test command will be run for each fix (Step 4), or _"No test command found — changes will be committed (and, in PR mode, pushed) without running tests."_ Approving the plan accepts that.

#### Reply style (PR mode)

The reply style depends on how many **inline review threads** (comments attached to a file/line) the plan responds to, whether actioned or declined:

| Inline threads to respond to | Reply style |
|------------------------------|-------------|
| 3 or fewer | **Individual replies** — one reply per thread, then resolve it |
| More than 3 | **Single grouped reply** — one PR-level comment covering every thread; the inline threads get **no reply of their own**, only a "resolved" status |

- Count only inline threads.
- Replies are always posted as ordinary comments: a thread reply on an inline thread, or a PR-level comment otherwise.
- Review bodies have no thread to reply in, so they are answered with a PR-level comment that @-mentions the reviewer and links the review. In grouped style, fold them into the grouped reply instead of posting a separate comment.
- A merged item is answered once: on its inline thread (individual style) or as one bullet in the grouped reply. That answer covers all its other sources too — do not reply to them separately.
- Do not count items the user chose to skip or that are still awaiting a clarification.

The plan also lists **reviewers to re-request** after publishing (Step 7): every human reviewer, other than `<pr-author>`, with at least one item in this plan that is actioned or declined. Reviewers whose items were all skipped are left out. Never re-request bots (`[bot]` logins, Copilot, etc.).

#### Reply file (PR mode)

Write the draft replies to `<reply-file>` = `<tmpdir>/review-replies-pr<number>.md`, where `<tmpdir>` is:

- the session's scratchpad directory, if the harness provides one (e.g. Claude Code's per-session scratchpad), otherwise
- a fresh directory created for this run: `mktemp -d -t review-replies.XXXXXX`

Never use a fixed shared path (such as `/tmp/review-replies.md`).

The reply file is the skill's working copy — the text that gets published in Step 7 — not something the user has to open. The user reviews the replies in the plan and asks for changes in the conversation; apply each change to the reply file and show the updated reply text again. (Mention the file's full absolute path once, for anyone who prefers to edit it directly.)

Use the reply style chosen above.

**Individual replies** (3 or fewer inline threads) — one entry per actioned or declined comment:

```markdown
# Review Replies
<!-- Edit 'reply' text freely. Set skip: true to skip posting a comment. -->

## 1. Comment #<id> (@<reviewer>)

> <original comment text quoted here>

skip: false

reply: |
  <proposed reply text here>

---

## 2. Review #<id> (@<reviewer>)

> <review body quoted here>

skip: false

reply: |
  @<reviewer> re: your review (<review url>) — <proposed reply text here>

---

## Re-request review
<!-- Remove a login to not re-request them. Leave empty to re-request nobody. -->

reviewers: <login1>, <login2>
```

A merged item gets one entry, headed by its inline thread if it has one (otherwise by its first source), with an `also: Review #<id>, Comment #<id>` line under the header.

**Single grouped reply** (more than 3 inline threads) — one `## Grouped reply` entry that carries the reply text, plus one `resolve` entry per thread. The threads receive no reply; they are only resolved:

```markdown
# Review Replies
<!-- Edit 'reply' text freely. Set skip: true to skip posting the grouped comment.
     Set resolve: false to leave a thread open. Threads never get an individual reply. -->

## Grouped reply

skip: false

reply: |
  Thanks @<reviewer> — addressed the review comments in <sha-range>:

  - `<file>:<line>` (#<id>) — <fixed: what changed | declined: reason>
  - `<file>:<line>` (#<id>) — <fixed: what changed | declined: reason>
  - ...

---

## Resolve

### 1. Comment #<id> (@<reviewer>) — `<file>:<line>`

> <original comment text quoted here>

resolve: true

---

## Re-request review
<!-- Remove a login to not re-request them. Leave empty to re-request nobody. -->

reviewers: <login1>, <login2>
```

If the inline threads come from several reviewers, still post one grouped reply and mention each reviewer once. Review-body items go into the grouped reply as bullets (`- Review #<id> — <fixed | declined: reason>`).

Drafts may contain `<sha>` / `<sha-range>` placeholders for commits that do not exist yet. Filling them in with the real SHAs after Step 4 is the **only** change you may make to approved reply text without asking.

#### Approval — the only gate

Present the plan — in PR mode with every reply's full text inline — and prompt:

- **PR mode:** _"Review the plan above, including the full reply texts and the reviewers to re-request. Tell me any changes (reword a reply, skip one, drop a reviewer), or reply 'approved' to implement, test, push and post without further confirmation — I'll stop and come back to you only if something goes wrong."_
- **Local mode:** _"Review the plan above. Reply 'approved' to implement, test and update the save file without further confirmation — I'll stop and come back to you only if something goes wrong."_

Get answers to any clarifications and "likely already addressed" confirmations first, and update the plan and reply file with them before asking for approval.

**PR mode:** after approval, re-read and validate the reply file — it must match the reply texts last shown to the user (they may also have edited it directly; if so, show the changed replies before going on):
- **Individual replies:** every entry must have a `## <n>. Comment #<id>` or `## <n>. Review #<id>` header, a `skip:` field (true/false), and a `reply:` block
- **Grouped reply:** there must be exactly one `## Grouped reply` entry with a `skip:` field and a `reply:` block, and every inline thread from the plan must appear under `## Resolve` with a `resolve:` field (true/false) and **no** `reply:` block
- **Both styles:** there must be exactly one `## Re-request review` section with a `reviewers:` field (a comma-separated list of logins, possibly empty)
- If an entry is malformed, fix the structure yourself without changing the reply text. If it cannot be fixed without guessing (e.g. after a direct edit by the user), show the affected entry, say what is wrong, and ask. Do not start implementing until the file is valid.

Approval covers everything up to the Summary: the commits, the push, posting the replies as they stand in the file, resolving threads and re-requesting review. Do not ask again unless a stop condition (Step 5) is hit.

### 4. Implement

Hand the work to subagents, one item at a time. You (the main session) only coordinate. You do not edit code yourself, and you pass each subagent everything it needs in its prompt.

Before the first item, run `git status`. If a file the plan touches already has uncommitted changes, stop and ask.

Work through the plan's actioned items top-down (blockers first), **sequentially** — never two at once. For each item:

1. **Implement.** Spawn a fresh `general-purpose` subagent with:
   - the item: its source(s), the reviewer's comment and thread context, the proposed fix, and (PR mode) the approved reply text
   - the files and code it concerns, and the project's conventions (from CLAUDE.md etc.)
   - the test command from the plan

   Brief it to implement **only this item**, add or update tests where the fix changes behaviour, and run the tests relevant to the changed files. This is the only place tests are run. It must **not** stage, commit or push anything. If the code is not as the plan describes, the fix needs a different approach or other files, or the tests can't be made to pass within this item, it stops and reports instead of improvising. It reports back: changed files, the exact test command, its result (pass/fail counts, and the output of any failure), and any deviations from the proposed fix.

2. **Review and commit.** Spawn a *separate*, fresh `general-purpose` subagent; never reuse the implementer. Give it the same item details (proposed fix, approved reply text), the implementer's report, and the test command. Brief it to:
   - read the diff (`git diff`) and check that it does what the proposed fix says, and (PR mode) everything the approved reply claims; that it stays in scope (nothing unrelated changed, no files outside the item); and that it is correct and follows the repo's conventions
   - check the implementer's reported test run instead of running the tests again: the command is the plan's test command, it covers the changed files, and it passed. If no tests were run, they failed, or they don't cover the change, request changes. When the plan says no test command was found, skip this check
   - on **APPROVE**: stage only this item's files and commit, `git add <file1> <file2> && git commit -m "review: <summary>"`, then report the commit SHA. Never push
   - on **CHANGES_REQUESTED**: commit nothing and return a numbered, file-specific list of what is wrong

3. **On changes requested**, spawn a new implementer with the item details plus the reviewer's numbered feedback, then a new reviewer, as above. After **2** rounds of changes requested on the same item, treat it as a stop condition (Step 5).

Record each item's commit SHA as it lands. Do **not** push or post anything yet.

> **Larger plans:** the user can ask for the approved plan to be handed to the `build` skill (its foreman/crewman/inspector loop) instead. Do this only when asked, as it is much heavier. Publishing (Step 7) still happens here once it is done.

### 5. Check Against the Plan

Tests were run once per item in Step 4. Do not run them again here.

1. Show the user each item's commit SHA, test command and test result, as reported in Step 4
2. **PR mode:** fill the SHA placeholders in the reply file

**Stop conditions.** Stop — do not push, post or update the save file — and report back to the user if anything does not go according to the plan:

- tests still fail, or fixing them needs changes outside the plan
- a command fails unexpectedly (build, git, `gh`, …)
- an assumption in the plan turns out wrong: the code is not as described, a fix needs a different approach or touches files the plan did not mention, or an item turns out invalid or already fixed (including when the implementer subagent stops and reports this)
- what was implemented no longer matches what an approved reply says
- the reviewer subagent still requests changes after 2 rounds on the same item
- the branch has diverged from its remote, so the push would need a pull, rebase or force

When stopping, say what went wrong, what is committed locally, and that nothing has been pushed or posted; propose the change to the plan and/or replies, and wait for a new approval before continuing.

If nothing went wrong, continue straight to Step 6 — no second approval.

### 6. Record Outcomes

#### PR mode

No separate step — the replies were approved with the plan and are posted in Step 7.

#### Local mode — update save file

1. For each **actioned** finding: prepend `[RESOLVED]` to its severity cell — e.g. `🟡 Warning` → `[RESOLVED] 🟡 Warning`
2. For each **rejected** finding: prepend `[REJECTED]` to its severity cell — e.g. `🔵 Nit` → `[REJECTED] 🔵 Nit`
3. If any findings were rejected, append a **"Rejected Findings"** section to the save file body:

```markdown
### ❌ Rejected Findings

| # | Finding | Reason |
|---|---------|--------|
| 3 | <one-line summary> | <reason for rejection> |
```

### 7. Publish

#### PR mode

Run this without asking — it was approved with the plan. If any step fails, stop at once and report what has and has not been published (pushed? which replies posted? which threads resolved?); do not retry blindly and do not continue to later steps.

1. `git push` to publish the commits. If it is rejected (e.g. non-fast-forward), stop — never pull, rebase or force-push without asking
2. Read back `<reply-file>`:
   - **Individual replies** — for each entry:
     - `skip: true` → leave unresolved, do not post a reply
     - `Comment #<id>` (inline thread) → post the reply in that thread and mark it resolved
     - `Review #<id>` → post the reply as a PR-level comment (e.g. `gh pr comment`); there is nothing to resolve
   - **Grouped reply:**
     - `## Grouped reply` with `skip: false` → post it once as a single PR-level comment (e.g. `gh pr comment`); `skip: true` → post nothing
     - for each `## Resolve` entry with `resolve: true` → mark the review thread resolved **without posting a reply** (e.g. GraphQL `resolveReviewThread`); `resolve: false` → leave it open
3. **Re-request review** from every login in `## Re-request review` — one call: `gh pr edit <number> --add-reviewer <login1>,<login2>`. Do this last, after the push and all replies have gone through. If `reviewers:` is empty, skip this step. If a reply or the push failed, do not re-request — report the failure instead.
4. Delete `<reply-file>` (and the `mktemp` directory, if one was created) — only once everything above succeeded; after a failure, keep it so the remaining replies can be posted from it

#### Local mode

No push, no GitHub interaction — the user decides when to push.

### 8. Summary

#### PR mode

- ✅ Actioned & replied: `<n>` items (note whether replied individually or via a single grouped comment; note how many sources were merged by deduplication)
- ⏭️ Skipped (left unresolved): `<n>` items
- ❌ Rejected: `<n>` items
- 🔁 Review re-requested from: `@<login>, …` (or "nobody")

If any comments were rejected, list them:

```
### Rejected Comments

| Comment | Reviewer | Reason |
|---------|----------|--------|
| #<id>   | @<name>  | <reason> |
```

#### Local mode

- ✅ Resolved: `<n>` findings
- ❌ Rejected: `<n>` findings (with reasons listed)
- 📄 Save file updated: `./tmp/review-branch-<name>.md`

## Rules

- There is exactly one approval: the plan (with, in PR mode, the reply file) in Step 3. Never start implementing before it, and never ask for a second one when everything went according to the plan
- Stop and report on any stop condition (Step 5) or publish failure (Step 7); a changed plan or reply needs a new approval
- **PR mode:** never post replies that have not been approved, or that no longer match what was implemented; the reply file must pass validation first
- Never mark an item resolved without either implementing a fix or a documented rejection reason
- Implement each item with its own implementer subagent and get it reviewed and committed by a separate reviewer subagent, one item at a time. The main session does not edit code itself in Step 4
- Keep commits small and scoped to the item being addressed; stage only the files changed for each finding. Only the reviewer subagent commits, and only after approving
- Do not rewrite unrelated code while addressing review findings
- If a fix introduces risk, flag it to the user before implementing
- **PR mode:** when responding to more than 3 inline threads, never post per-thread replies — one grouped PR-level comment plus "resolved" status only
- The reply file lives in the session's scratchpad (or a per-run `mktemp -d` directory), never a fixed shared path, and must never be staged or committed
- **Local mode:** do not push — the user decides when to push
- Never auto-resolve a comment flagged as "likely already addressed" — always confirm with the user first
- **PR mode:** collect from all reviews, not just the latest; deduplicate before triage so each concern is answered exactly once
- **PR mode:** never respond to ordinary PR conversation comments — only unresolved inline threads and unanswered review bodies
- **PR mode:** re-request review only from the human logins in the approved reply file, and only after the push and all replies succeeded; never re-request bots
